Создайте понятный прототип, который распределяет заявки между инженерами, 
строит маршруты, показывает их на карте и умеет перестраивать план при изменениях.

работающий алгоритм, понятный интерфейс и убедительную демонстрацию. 
1. Контекст и актуальность задачи
Задача от «Билайн Бизнес» связана с созданием интеллектуального сервиса планирования 
рабочих маршрутов для выездных инженеров. Сегодня такие специалисты ежедневно берут 
в работу множество заявок, но при ручном распределении сложно одновременно учитывать 
квалификацию сотрудников, доступность транспорта, время визитов и срочные изменения 
в течение дня. 
Участникам 
предстоит 
разработать 
веб-сервис, 
который 
сможет 
автоматически 
распределять 
заявки,

оптимальные 
маршруты, 
учитывать 
ограничения 
и при необходимости оперативно перестраивать план работ. Решение должно также показывать 
итоговый маршрут на карте и объяснять причины выбранного варианта. 
Представьте начало рабочего дня: есть список заявок и несколько инженеров. У каждого 
сотрудника свои навыки, график и доступный транспорт. У заявок есть адрес, длительность, 
желаемое время визита и требования к исполнителю. В течение дня может появиться срочная 
заявка или один из инженеров может стать недоступен. Диспетчеру нужен новый план 
за несколько минут.  
Цель кейса: сделать прототип помощника диспетчера, который предлагает выполнимый 
план и простыми словами объясняет своё решение. 
2. Описание задачи
Разработайте веб-приложение, которое получает тестовый список заявок и инженеров, 
автоматически распределяет работы и строит маршрут для каждого исполнителя. 
2.1. Что должно уметь решение 
1. Загружать готовые тестовые данные из CSV или JSON либо использовать встроенный
демонстрационный набор. 
2. Распределять заявки между инженерами. 
3. Определять порядок посещения адресов для каждого инженера. 
4. Показывать маршруты и точки заявок на карте.

2.3. Что можно считать оптимальным маршрутом? 
Решение должно стремиться распределить все заявки с соблюдением обязательных 
ограничений. Если это невозможно, допускаются неназначенные заявки с обязательным 
объяснением причины. Для сравнения допустимых планов используются две обязательные 
метрики: 
• выполнение всех заявок наименьшим количеством персонала: учитывается количество 
уникальных исполнителей, которым назначена хотя бы одна заявка; 
• пробег по маршруту каждого исполнителя: расстояние отображается по каждому 
исполнителю отдельно и суммарно по всему плану.

Команда может дополнительно использовать другие критерии оптимизации, например, 
минимальное время в пути или максимальное число выполненных заявок, если полный план

Не требуется доказывать математический оптимум. Подойдёт готовая библиотека, простой 
эвристический алгоритм или собственная понятная логика. Для единого сравнения базовый 
вариант задаётся так: заявки обрабатываются по порядку поступления и назначаются первому по 
порядку во входных данных доступному инженеру, который удовлетворяет обязательным 
ограничениям; порядок посещения соответствует порядку назначения. Глобальная оптимизация 
в базовом варианте не выполняется. 
2.4. Формат входных данных 
Решение должно стремиться распределить все заявки с соблюдением обязательных

метрики: 
Сущность 
Минимальные поля

ID, координаты или адрес, длительность в минутах, начало и конец

Инженер

Событие

Тип события (срочная заявка / отмена заявки / недоступность инженера),

Рекомендуемые единицы: время — HH:MM, длительность и время в пути — минуты, 
расстояние — километры, координаты — широта/долгота. 
2.4.1. Справочники входных данных 
Требуемый навык: 
1. Локальные работы 
2. Работы на подключение и дозаказы 
3. Аварийные работы 
Каждая заявка содержит один требуемый навык из справочника. У исполнителя может быть 
от 1-го до 3-х навыков одновременно.

Для каждого исполнителя указывается один тип транспортного средства. В заявке

2.4.2. Формат результата
• Для каждого исполнителя — упорядоченный список заявок, плановое время 
прибытия/начала работ и пробег по маршруту. 
• Для каждой заявки — назначенный исполнитель либо статус «не назначена». 
• Для неназначенной заявки — явная причина понятным диспетчеру языком.
• Для плана в целом — количество задействованных исполнителей, пробег по каждому 
исполнителю и суммарный пробег. 
• После перепланирования — наглядное отображение того, какие назначения, порядок 
заявок или маршруты изменились. 
• Для выбранного маршрута — краткое объяснение, какие ограничения и факторы 
повлияли на решение.

4. Требования к презентации и демонстрации
На защите покажите один короткий и понятный сценарий. Основной формат —
live-демонстрация работающего прототипа. В качестве альтернативного способа демонстрации 
допускается заранее подготовленная видеозапись работы решения. 
1. Загрузите или откройте тестовый набор данных. 
2. Запустите автоматическое планирование. 
3. Покажите распределение заявок и маршруты на карте. 
4. Откройте одну заявку и объясните, почему она назначена выбранному инженеру. 
5. Добавьте срочную заявку, отмените существующую или сделайте инженера недоступным. 
6. Перестройте план и покажите, что изменилось.

Организаторам рекомендуется предоставить участникам обезличенный или синтетический

чтобы проверить алгоритм, карту и сценарий перепланирования. 
• CSV/JSON с заявками и инженерами; 
• описание полей и единиц измерения; 
• один базовый сценарий рабочего дня; 
• одно событие для перепланирования; 
• пример ожидаемого формата результата. 
Тестовый набор должен позволять проверить все обязательные ограничения: в данных 
должны встречаться все три навыка, разные комбинации навыков у исполнителей, все типы 
транспорта, пересекающиеся временные окна и хотя бы один конфликт, при котором простое 
последовательное распределение даёт менее эффективный план. 
Если готовый набор не будет предоставлен, команда может самостоятельно создать 
синтетические данные по тем же правилам и описать принятые допущения.
