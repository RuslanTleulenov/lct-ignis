# 02. Архитектура и стек

## 1. Стек (решено)

| Слой | Выбор | Почему |
|---|---|---|
| Солвер | **Google OR-Tools 9.15** (`routing`) | Единственный зрелый бесплатный VRPTW-движок, где из коробки есть ровно то, что просит ТЗ: временные окна, ограничение «какой ТС может обслужить узел» (= квалификация/оборудование), разные матрицы по типу транспорта, перерывы, необязательные визиты со штрафом, warm start |
| Backend | **Python 3.11 + FastAPI + Pydantic v2 + Uvicorn** | OR-Tools — Python-first; FastAPI даёт схемы и WebSocket из коробки |
| Хранилище | **SQLite + SQLAlchemy 2.0** | Docker на машине нет; объёмы хакатонные; файл БД коммитится/переносится одной копией |
| Frontend | **React 18 + TypeScript + Vite** | Живой Гант и diff-режим на серверном рендеринге делать больно |
| Карта | **MapLibre GL JS** + растровые OSM-тайлы | Без ключей и без вендор-лока; при наличии ключа подменяется на MapTiler/2ГИС |
| Состояние | локальное в `App.tsx` | Приложение одноэкранное, TanStack Query и Zustand добавили бы слой без выгоды |
| UI-кит | свой CSS | Меньше конфигов и нечему сломаться накануне защиты; тёмная обвязка + светлая карта |
| Realtime | WebSocket (FastAPI) | Push нового плана после перепланирования, без поллинга |

> Стек фронтенда сознательно урезан против первоначального замысла: из зависимостей
> остались только `react`, `react-dom` и `maplibre-gl`. Tailwind, shadcn/ui,
> TanStack Query и Zustand выброшены — на одном экране они не окупаются, а каждый
> тянет свою конфигурацию.

**Python 3.11 (`py -3.11`), не 3.13** — на машине 3.13 стоит из Microsoft Store, у неё
исторические проблемы с путями вне профиля пользователя, а проект живёт на `D:`.
OR-Tools доступен для обеих версий (9.15.6755), так что теряем только принципиально.

**Docker не используем.** Ни для БД, ни для OSRM. Всё поднимается двумя командами.

## 4. API (черновик)

### Справочники
```
GET    /api/reference/work-types          типы работ + матрица «работа → оборудование»
GET    /api/reference/equipment           оборудование, склады, наличие
GET    /api/engineers                     инженеры: навыки, смены, транспорт
```

### Заявки и план
```
GET    /api/jobs?date=2026-08-12
POST   /api/jobs                          новая заявка → триггер перепланирования
PATCH  /api/jobs/{id}                     смена статуса (выполнена / затянулась / отменена)

POST   /api/plan/build                    {date, weights, engineer_ids?} → plan_id
GET    /api/plan/{id}                     маршруты, KPI, метрики
POST   /api/plan/{id}/replan              {events:[...]} → новый план + diff
GET    /api/plan/{id}/compare?baseline=greedy   эффект vs «ручное» планирование
```

### Объяснимость
```
GET    /api/plan/{id}/explain/{job_id}    почему этот инженер, это время, этот порядок
GET    /api/plan/{id}/why-not/{job_id}    почему НЕ назначено: разбор по всем инженерам
```

### Ручное вмешательство диспетчера
```
POST   /api/plan/{id}/lock                закрепить визит за инженером (солвер не тронет)
POST   /api/plan/{id}/move                перенести визит → валидация допустимости
```

### Динамика и импорт
```
WS     /ws/plan/{id}                      стрим обновлений плана
POST   /api/sim/start | /tick | /stop     симулятор рабочего дня
POST   /api/import                        загрузка CSV/XLSX своего датасета
```

## 5. Ключевые архитектурные решения

### 5.1. Почему OR-Tools, а не своя эвристика

Каждое требование ТЗ ложится на конкретный механизм библиотеки:

| Требование | Механизм OR-Tools |
|---|---|
| Временные окна | `AddDimension("Time")` + `CumulVar(index).SetRange(e, l)` |
| Квалификация и оборудование | `routing.VehicleVar(index).SetValues([допустимые инженеры])` |
| Разная скорость авто/пешком | `SetArcCostEvaluatorOfVehicle(callback, vehicle)` — своя матрица на ТС |
| Обед | `SetBreakIntervalsOfVehicle(...)` |
| Рабочая смена | границы `CumulVar` в стартовом и конечном узлах маршрута |
| Заявку можно не брать | `AddDisjunction([index], penalty)` — штраф вместо жёсткого требования |
| Приоритет / SLA | размер штрафа в disjunction + soft-границы окна (`SetCumulVarSoftUpperBound`) |
| Быстрое перепланирование | `ReadAssignmentFromRoutes(prev_routes)` — старт из прошлого решения |
| Мульти-депо | массивы `starts[]` / `ends[]` вместо одного депо |

Писать это руками = минус два дня и худшее качество маршрутов.

### 5.2. TravelTimeProvider — абстракция поверх времени в пути

```python
class TravelTimeProvider(Protocol):
    def matrix(self, points, mode, departure_min) -> Matrix: ...
    def minutes(self, a, b, mode, departure_min) -> int: ...
    def distance_km(self, a, b, mode) -> float: ...
```

**Основная реализация — `OsmRoutingProvider`: маршрутизация по реальной
дорожной сети.** Граф строится из выгрузки OpenStreetMap (см. §5.6), даёт время
в пути, длину пути и геометрию для карты. Три профиля: автомобиль с учётом
односторонних улиц, пешком и пешком + метро.

**Запасная — `HaversineProvider`**: прямая × 1.35 ÷ скорость × коэффициент
пробок. Включается автоматически, если выгрузки OSM нет, и пишет об этом в лог.
Молчать нельзя: разница в цифрах достигает полутора раз.

`CachedProvider` — обёртка с кешем матриц для запасного варианта; у OSM-провайдера
кеш свой, встроенный.

### 5.3. Перепланирование ≠ пересчёт с нуля

```
событие → снимок состояния на текущий момент T:
    визиты со статусом done/in_progress   → зафиксированы, из модели исключены
    текущая позиция инженера              → новый start-узел маршрута
    оставшееся время смены                → новое окно маршрута
    остальные визиты + новая заявка       → пересчитываются
    предыдущее решение                    → warm start (ReadAssignmentFromRoutes)
    штраф за перестановку сообщённых клиенту визитов → w_stability
    лимит времени солвера                 → 3 секунды
```

На выходе — не только новый план, но и **diff**: у кого что изменилось.
На демо это выглядит так: прилетела аварийная заявка → через 3 секунды
подсветились два маршрута, остальные десять не тронулись.

### 5.4. Объяснимость считается, а не выдумывается

Источник — само решение солвера:

- **почему этот инженер**: перебор допустимых альтернатив с оценкой дельты
  целевой функции («Петров: +18 мин пути и нарушение окна заявки #22»);
- **почему это время**: `CumulVar` прибытия, слэк ожидания, границы окна;
- **почему НЕ назначено**: отдельный `FeasibilityChecker` прогоняет заявку по
  всем инженерам и возвращает первое нарушенное жёсткое ограничение с разбивкой
  («нет допуска — 7 чел., нет оборудования — 3, окно недостижимо — 5»).

LLM-слой (опционально, поверх) только переводит эти факты в связный текст.
Никаких «нейросеть решила» — цифры всегда настоящие.

### 5.5. Baseline для сравнения

Без цифры эффекта решение не продаётся. Реализуем «как сейчас у диспетчера»:
жадное назначение — заявки в порядке поступления, каждая уходит первому
подходящему свободному инженеру, объезд в порядке назначения. Сравниваем:
время в пути, нарушения SLA, число назначенных заявок, разброс загрузки.

## 7. Что делаем в первую очередь (порядок работ)

1. Датасет + генератор — без данных ничего не проверить.
2. `TravelTimeProvider` (haversine) + матрица.
3. Солвер: базовый VRPTW → добавляем квалификацию → оборудование → транспорт.
4. REST `/plan/build` + KPI.
5. Карта + Гант в UI (минимально, но живые).
6. Перепланирование + diff.
7. Объяснимость (`explain`, `why-not`).
8. Baseline и экран сравнения.
9. Симулятор дня, ручное вмешательство, импорт.
10. Полировка UI и сценарий защиты.
